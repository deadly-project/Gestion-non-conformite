------------------------------------------------------------------------
2. DIAGNOSTIC (état initial)
------------------------------------------------------------------------
La compilation échouait avec des erreurs de type :

  - "bad source file ... file does not contain class com.example.smq.service.JournalService"
  - "duplicate class: com.smq.service.JournalService"
  - 148 erreurs "cannot find symbol" (getStatut(), setStatut(), isActif(),
    getRole(), setNc(), getNbReouvertures(), setDateCloturation(), ...)

Cause racine : les fichiers Java étaient physiquement rangés dans le dossier
com/example/smq/ mais déclaraient dans leur en-tête :

      package com.smq.xxx;

C'est-à-dire un paquet ne correspondant PAS à leur répertoire réel.

Par ailleurs, il existait une incohérence : un seul fichier
(AttachmentService.java) déclarait déjà « package com.example.smq.service; »
alors que les 44 autres déclaraient « com.smq.* ». Ce mélange de paquets
faisait que le compilateur ne retrouvait plus les classes les unes par
rapport aux autres (d'où les « cannot find symbol » et « duplicate class »).

------------------------------------------------------------------------

Aucune ligne de logique n'a été modifiée. Les seules modifications portent

  a) Déclarations « package » (45 fichiers) :

        package com.smq.entity;         -> package com.example.smq.entity;

     (soit 44 fichiers « com.smq.* » + AttachmentService déjà en

  b) Imports internes (toutes les occurrences) :

  c) Aucune autre modification : ni méthode, ni attribut, ni annotation,

Preuve : une comparaison automatique de chaque fichier corrigé avec sa
version d'origine (en neutralisant uniquement les lignes « package » et

6. REMARQUE (hors périmètre de correction, à titre informatif)
------------------------------------------------------------------------
La classe principale est dans le paquet
  com.example.backend_gestion_nc
alors que les classes SMQ sont dans
  com.example.smq

Le scan automatique de Spring Boot (@SpringBootApplication) ne détecte que
le paquet de la classe principale et ses sous-paquets ; il ne verra donc
pas automatiquement les entités/repositories/services sous com.example.smq.
Cela n'empêche PAS la compilation (objet de ce rapport) mais peut empêcher
le démarrage effectif de l'application. Si besoin, il suffirait d'ajouter
sur BackendGestionNcApplication une configuration de scan, par exemple :

      @SpringBootApplication(scanBasePackages = "com.example")
      @EntityScan("com.example.smq.entity")
      @EnableJpaRepositories("com.example.smq.repository")

Cette remarque n'a pas été appliquée afin de respecter la consigne
« ne rien changer d'autre ».
